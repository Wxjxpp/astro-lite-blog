# 自己打包 N67 Chaos 安装器 —— 操作教程（基于 Chaos-9Pro-3.1.190.bin 实测）

本文所有数字都来自对 `Chaos-9Pro-3.1.190.bin` 的实测和 loader 反汇编，
不是估算。换一个安装包时数字会变，但格式和公式不变。

需要的文件：`n67_chaos_extract.py`（拆包/解压/校验）、
`p67_pack_official.py`（容器打包）、`cpk1_pack.py`（压缩并切分片）。
只要 Python 3，无第三方依赖。

---

## 第 1 步：拆包

```bash
python3 n67_chaos_extract.py Chaos-190.bin work/
```

`work/` 下会得到：

- `00_main.lua` … `55_chaos-rl.dat`：56 个原始资源条目
- `preview.block`：容器预览块
- `spec.json`：可直接喂给打包脚本的清单（含版本号、风格名、id、文件名）
- `CHAOS_IMAGE.bin`：**解压后的真正 Chaos 镜像**（按 `0x1D100000` 链接）
- `chaos_rl_decoded.json`：CRL1 重定位表解码结果
- `main_lua_readable.txt`：main.lua 去掉内嵌二进制长字符串后的可读代码

本包实测值：

| 项目 | 值 |
|---|---|
| 资源条目 | 56 |
| 分片 `chaos-NN.dat` | 49 个（00–48） |
| 镜像总大小 `CHAOS_SIZE`（含 .bss） | 2000468 |
| 实际落盘覆盖长度 | 1589692 = `0x1841BC` |
| 重定位站点 | 4172 个 |
| 链接基址 | `0x1D100000` |
| 重定位表 FNV-1a | `0xD5176A26` |
| 容器版本字段 | `0x00010000`（1.0.0） |
| 风格名 | `格式1` |

拆包时会自动核对每个分片的 FNV-1a、CRL1 的 FNV-1a，以及
4172 个站点值是否都落在 `[0x1D100000, 0x1D100000+CHAOS_SIZE]`。
全部通过才会继续，否则直接报错。

### CPK1 分片到底是什么

每个 `chaos-NN.dat` 不是裸数据，而是**一个 0x8000 输出窗口的 LZ 压缩流**：

```
"CPK1" + u32(窗口起始偏移 f1) + u32(该窗口解压后大小 f2)
       + u32(压缩流长度 f3) + u32(FNV-1a(压缩流)) + 压缩流
```

LZ 格式与 main.lua 里 `data_assets` 的解压器相同：

- 取 1 字节 `t`
- `t < 128`：字面量，复制随后 `t` 字节（`t` 必须是 1..127）
- `t >= 128`：回溯，读 u16 距离 `d`，复制 `t-128+4` 字节（允许重叠）

每个分片独立压缩，回溯不会跨窗口。49 个窗口解压后正好拼成
1589692 字节，剩余到 2000468 的部分是 .bss（不落盘）。

## 第 2 步：原样重打包（保险可用包）

第 1 步跑完直接：

```bash
python3 p67_pack_official.py build work/spec.json rebuilt.bin
```

本包实测：`rebuilt.bin` 与原件 **875596 字节、SHA256 完全相同**。

之所以能做到字节一致，是修掉了旧版脚本的三处差异：

1. 容器版本字段：从 `spec.json` 的 `version` 读（本包 `0x00010000`），
   不再固定写回退值。
2. pair 2–5 的偏移：原包指向 `props_off`（本包 `0x4D8`），旧脚本写成了
   `SCRIPT_OFF`。
3. 风格名：从 `spec.json` 的 `styleName` 读（本包 `格式1`），不再用默认值。

因此"原样重打包"这一步现在不需要任何手改。

## 第 3 步：换成新的 chaos_sup（真正的移植）

前提：先用官方仓库在本机编出新的 `chaos_sup.ko`（Rust nightly +
`thumbv8m.main-none-eabi` + clang/LLVM）。仓库目前只带 `10p-3.101.043`
的符号表；要在 N67 9 Pro 上跑，还需要 N67 固件的符号/地址映射，这一步
不是纯打包能解决的。

### 3.1 ELF → 扁平镜像

用官方 `tools/fix_ko_layout.py` / `tools/build_ko.sh` 把 `.ko` 按
section 的 `sh_addr` 摊平。得到的镜像必须是**按 `0x1D100000` 链接**的，
因为旧 loader 和 `main.lua` 的 `0x1D100000` 常量都是按这个基址写死的。
如果新 ELF 链接基址不同，必须先重定位/重链接到 `0x1D100000`，不能直接摊平。

### 3.2 找 `chaos_ctor` 偏移和模块大小

```bash
llvm-nm dist/10p-3.101.043/chaos_sup.ko | grep chaos_ctor
```

注意：`nm` 给的是**链接期虚拟地址**（本包是 `0x1D1xxxxx` 形式），
`main.lua` 要的是**模块内偏移**：

```
offset = nm_value - 0x1D100000
```

本包旧值是 `447949`（`0x6D5CD`），对应 nm 地址 `0x1D76D5CD`。
不要直接把 nm 的地址填进去。

模块总大小（含 .bss）取
`max(sh_addr + sh_size) - min(sh_addr)`，不要简单累加各 section
的 `sh_size`（对齐和空隙会多算）。填到 `main.lua` 的 `CHAOS_SIZE`，
并作为 `cpk1_pack.py` 的第三个参数。

### 3.3 重定位表 `chaos-rl.dat`

格式已完全确认：

```
"CRL1" + u32(站点数) + u32(镜像总大小)
       + u32(FNV-1a(站点列表)) + 站点数 × u32(升序、4 字节对齐的偏移)
```

- 站点来自新 ELF 的 `R_ARM_RELATIVE` 重定位项（`llvm-readelf -r`），
  取值是模块内偏移；排序、去重。
- FNV-1a 是对**站点列表的 u32 小端字节**计算：
  `h=0x811C9DC5`，每字节 `h=(h^b)*0x01000193 mod 2^32`。
  本包已用这个方法复算得到 `0xD5176A26`，与原文件一致。
- **站点值不需要"编码"**：镜像里这些位置本来就存着按 `0x1D100000`
  链接好的绝对地址。设备侧公式是：

  ```
  new = old - 0x1D100000 + 运行时执行基址
  ```

  旧教程里"占位值 = 0x1D100000 + 站点偏移"的猜测是错的，
  它只对恰好指向自身的 105 个点成立。不要再按那个公式改数据。

### 3.4 压缩并切分片

```bash
python3 cpk1_pack.py 新的扁平镜像.bin work/newchunks/ 2000468
```

脚本会：

- 按最后一个非零字节确定有效覆盖长度（4 字节对齐），只生成有数据的窗口；
- 每个窗口做上面的 LZ 压缩；
- 自动写入 FNV-1a，不再是占位 0；
- 打印需要同步到 `main.lua` 的 `CHAOS_SIZE`、覆盖长度、分片数。

本包用这个脚本重压 `CHAOS_IMAGE.bin`，49 个分片合计 615513 字节
（官方 612290 字节，差 0.5%），解压回读逐字节一致。

### 3.5 main.lua 里要同步的 7 个常量

都在 `load_chaos()` 里：

| 代码里的值（本包） | 含义 | 来源 |
|---|---|---|
| `CHAOS_SIZE` = 2000468 | 镜像总大小（含 .bss） | 3.2 的区间算法 |
| `CHAOS_EXEC+447949` 的 `447949` | `chaos_ctor` 模块内偏移 | nm 地址 − `0x1D100000` |
| `info` 第 3 个字段 = 1589692 | **分片覆盖长度**（最后一个分片 `f1+f2`），不是 body 长度之和 | `cpk1_pack.py` 输出 |
| `info` 第 4 个字段 = 49 | 分片数 | `cpk1_pack.py` 输出 |
| `info` 第 5 个字段 = 4172 | 重定位站点数 | `chaos-rl.dat` 头部 |
| `info` 第 6 个字段 = `0x1d100000` | 链接基址 | 必须与新镜像一致 |
| `info` 第 7 个字段 = `0xD5176A26` | 站点列表的 FNV-1a | 3.3 公式 |

loader 会检查：

- 分片数 == `ceil(覆盖长度 / 0x8000)`；
- 每个分片的 `f1` 从 0 开始连续递增、`f2` 等于剩余窗口；
- CRL1 的站点数、总大小、FNV 与 `info` 一致；
- 每个站点值都在 `[0x1D100000, 0x1D100000+CHAOS_SIZE]`；
- 所有分片压缩流的 FNV 与各自头里的字段一致。

所以这 7 个常量任何一个填错，都会在加载阶段直接失败，而不是"能跑但行为怪"。

## 仍然存在的风险

1. **ABI/固件地址兼容性**：这是 10p 的 `chaos_sup` 要跑在 N67 9 Pro 上，
   最大的不确定性不是打包格式，而是模块里引用的固件函数/数据结构地址
   是否适用于 N67 3.1.190。旧移植版之所以能跑，是因为做过一套 10p→N67
   的地址适配。新版本必须重复这件事（可参考仓库 `ports/rw6` 的锚点映射做法）。
2. **`.bss` 与堆布局**：`CHAOS_SIZE` 包含未落盘的 .bss，loader 依赖
   `malloc` 出来的内存初始为零。如果新模块对 .bss 有额外初始化要求，
   需要确认 loader 的行为与旧版一致。
3. **实机验证**：先只换分片/重定位表、保留旧 `chaos_ctor` 与 `main.lua`
   其余部分，确认 `/data/chaos-n67.log` 和 `/data/chaos-n67.mark` 能写出来，
   再逐步替换。不要一次性全换。

旧的"CPK1 4 字节校验未知"和"重定位编码未知"这两条风险已经排除：
前者是压缩流的 FNV-1a，后者是标准的链接基址重定位。

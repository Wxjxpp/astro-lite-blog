# 自己打包 N67 Chaos 安装器 —— 操作教程

默认你已经下载了这轮产出的三个脚本：`n67_chaos_extract.py`（拆包）、
`p67_pack_official.py`（容器打包，仓库原版）、`cpk1_pack.py`（给 Chaos 二进制
切分片）。只要 Python 3 就行，不需要额外依赖。

## 第 1 步：拆包，看清楚现在的包里有什么

```bash
python3 n67_chaos_extract.py Chaos-190.bin work/
```

会在 `work/` 下生成：
- `00_main.lua` … `43_chaos-rl.dat`：44 个原始资源条目
- `CHAOS_BIN_reconstructed.bin`：拼好的完整 Chaos 模块（不含末尾全零 .bss）
- `chaos_rl_decoded.json`：重定位表解码结果
- `main_lua_readable.txt`：main.lua 去掉二进制长字符串后的可读代码

先跑这一步，后面不管做哪种修改都从这里的文件改起。

## 第 2 步：只是想验证/备份，原样重打包

第 1 步跑完，`work/` 下已经有现成的 `spec.json`（自动生成，把 44 个文件和
preview 块都列好了），直接：

```bash
cp p67_pack_official.py work/   # 或者在 work/ 的上一级跑，把路径对应改一下
python3 work/p67_pack_official.py build work/spec.json rebuilt.bin
```

产出的 `rebuilt.bin` 大小会和原包完全一致（733082 字节），内容也完全一致，
但 SHA256 不会完全相同——容器头里有 3 处纯装饰性字段（版本号、一个内部
基准定义的偏移写法、"风格名"文本）用的是脚本默认值，跟原包的习惯写法不
一样，不影响任何功能。如果你想要字节级一模一样（比如要对着官方签名校验），
告诉我，我可以把那几处差异也补进脚本默认值。如果你只是想要一个"肯定能用"
的安装包，到这一步就够了。

## 第 3 步：想换成新的 chaos_sup（这是真正的"移植"）

**前提**：你得先在装好 Rust nightly + `thumbv8m.main-none-eabi` + clang/LLVM 的
本地环境里，用官方仓库跑出一个新的 `chaos_sup.ko`（走 `10p-3.101.043`，目前
唯一官方支持的目标）。这一步我这边做不了（见上一条回复），必须你自己编。

拿到新的 `chaos_sup.ko` 之后：

### 3.1 把 ELF 变成扁平二进制镜像

`chaos_sup.ko` 是 ELF 格式，不能直接切分片。需要先按各个 section 的
`sh_addr` 把它摊平成一段连续内存镜像（这正是官方 `fix_ko_layout.py` 已经
做过的事——如果你是用 `tools/build.py` 走完整流程产出的，`dist/<fw>/` 目录
下应该已经有现成的、布局修好的产物；具体是哪个文件，去看
`tools/build_ko.sh` 和 `docs/BUILD.md` 里"构建流程"那张图，确认
`fix_ko_layout.py` 的输出文件名）。

### 3.2 找到新的 `chaos_ctor` 偏移和模块总大小

构建产物在 strip 之前应该还带符号表，用：

```bash
arm-none-eabi-nm dist/10p-3.101.043/chaos_sup.ko | grep chaos_ctor
```

或者 `llvm-nm`（docs/BUILD.md 提到构建用的是 `rust-lld`，符号表读取用
`llvm-objcopy`/`llvm-nm` 更稳）。记下这个地址——就是 `main.lua` 里
`(CHAOS_EXEC+447949)|1` 这一行要改的那个数字（`447949` 换成新偏移）。

模块总大小（含 `.bss`）用 `size` 命令或者 `readelf -S` 把各 section 的
`sh_size` 加起来算，这个数字要填进：
- `main.lua` 里的 `CHAOS_SIZE`
- `cpk1_pack.py` 的第三个参数

### 3.3 切分片

```bash
python3 cpk1_pack.py 新的扁平镜像.bin work/newchunks/ <模块总大小>
```

会生成 `chaos-00.dat` ... `chaos-NN.dat`。**注意脚本里那 4 字节占位校验**——
我没能确认设备侧是否真的校验这 4 字节、校验的是什么算法，先填 0。如果装上
之后 Chaos 死活起不来，这是第一个该怀疑的地方。

### 3.4 重定位表（最大的坑，我没能完全搞清楚）

`chaos-rl.dat` 记录了模块里哪些位置需要在加载时"加上实际加载基址"修正。
我反汇编引导垫片后确认了：
- 文件头：`CRL1` + u32(重定位点个数) + u32(模块总大小) + u32(FNV-1a 哈希，
  初值 `0x811c9dc5`，质数 `0x01000193`，对整个重定位点列表或某种派生数据算的)
  + 重定位点偏移列表（u32，升序）。
- 校验机制对得上，但**具体每个重定位点怎么编码"占位值"、加载时怎么算出
  正确地址**，我验证的公式（占位值 = `0x1D100000` + 模块内偏移）在 4260 个
  点里只对了 105 个，说明不是通用规律。

这意味着：**如果你直接拿旧的 `chaos-rl.dat` 配新编译的二进制，重定位点的
位置和数量基本不可能对上**，新模块大概率加载后行为错乱甚至直接死机。

我建议的路线（按风险从低到高）：
1. **先不碰重定位表，只验证分片加载和 `chaos_ctor` 调用本身对不对**——
   如果你能让设备侧的日志文件 `/data/chaos-n67.log` 和
   `/data/chaos-n67.mark` 跑出来（main.lua 里 `log()`/`mark()` 两个函数
   专门写这两个文件，照抄这套诊断机制），至少能看到卡在哪一步。
2. 如果你有 Ghidra（没有的话装个免费的），把 `CHAOS_BIN_reconstructed.bin`
   和拆出来的那 4904 字节引导垫片一起丢进去反编译，重点看偏移 `2653` 那个
   函数的后半段（我只手工看到 `0xf2e` 左右，函数应该还没完，Capstone 线性
   反汇编到后面很容易因为遇到字面量池而乱码，Ghidra 的控制流分析会准得多）。
   理清楚之后把真正的编码公式告诉我，我可以把 `cpk1_pack.py` 和一个配套的
   `crl1_pack.py` 补全。
3. 实在搞不定重定位表，退而求其次：**只换 Chaos 里你真正需要的某个小功能
   模块**，而不是整个 `chaos_sup`，这样影响的重定位点少，排查范围小。

## 第 4 步：main.lua 里要同步改的常量

换新二进制后，`main.lua` 里至少这几处要对应更新（都在 `load_chaos()` 函数里）：

| 常量 | 含义 | 来源 |
|---|---|---|
| `CHAOS_SIZE` | 新模块总大小（含 .bss） | 第 3.2 步算出来的 |
| `(CHAOS_EXEC+447949)` 里的 `447949` | `chaos_ctor` 偏移 | 第 3.2 步的 nm 结果 |
| `info` 结构体里的 `1184294` | 旧包里"分片实际存储字节总和"，新包要重新算 | 把 `cpk1_pack.py` 跑出来的所有分片 `body` 长度加起来 |
| `info` 结构体里的 `37` | 分片个数 | `cpk1_pack.py` 输出的分片数量 |
| `info` 结构体里的 `4260` | 重定位点个数 | 你新生成的 `chaos-rl.dat` 里的个数 |
| `info` 结构体里的 `0x1d100000` | 第 3.4 节提到的那个常量，如果重定位公式和旧版一样这个不用改，如果你重新设计了编码方式就要跟着改 | 需要你自己核实 |
| `info` 结构体里的 `38537463` | 重定位表的 FNV-1a 哈希 | 重新计算 |

## 安全提示

改完之后先别直接刷：`main.lua` 里本来就有 `log`/`mark` 这套诊断机制，
建议先确认这两个日志文件能正常写出来再做下一步；手环这种设备虽然不太容易
真被"硬件级"搞坏，但 Chaos 崩溃/卡死大概率需要你手动恢复官方表盘，折腾一次
不是小事，建议按上面"先不碰重定位表"那条路线一步步来，别一次性全换。
